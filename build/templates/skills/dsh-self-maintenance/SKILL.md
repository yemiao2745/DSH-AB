# dsh 自身维护

安装根 = `{{DSH_AB_ROOT}}`（所有改动都在这个安装根里做）。**若与实际不符（例如安装目录被搬过位置），以 `DSH_AB.exe` 所在的目录为准。**
活动槽读 <安装根>\state\active.json。
随包 git：<安装根>\runtime\git\cmd\git.exe。

## 动手顺序

1. 提交快照：**改动 DSH-AB 或 dsh 自身之后，用安装根的 git 提交一份快照**（`<随包 git> -C <安装根> add -A`，然后 commit）。安装根一个仓库，两个槽都在里面；**提交什么、什么时候提交由你判断**。**DSH-AB 与安装程序都不做 git**，快照只有你在管。
2. 将非活动槽清空，把活动槽整份复制到非活动槽。
3. 在非活动槽里改 dsh 本体、插件、配置。
4. 在非活动槽里起 dsh（**需要测试端口时，自己找一个当前没被占用的端口，并告诉用户你用的是哪个**），确认真能起来、改动真生效。
5. 切槽生效之前，把活动槽里**这次对话相关**的数据同步到非活动槽：同名覆盖，**别盖掉你在第 3 步改好的东西**；具体带哪些、怎么带，你自己判断。**本次对话的最后几条可能带不过去**，把这一点如实告诉用户。
6. 在 `<安装根>\state\pending.json` 里登记「槽位切换」（也可以让用户在托盘登记），再由用户点「重启」。
7. 提交快照。
8. 每完成一次修改都提交一次快照，工作区不留未提交的改动。

## 日志（排查错误先看这里）

- 三档：**off 只记 error**；**auto 再加 warn 与 debug**；**full 全记**，含 dsh 子进程输出（每行带 `child-slot-a` / `child-slot-b` 标明是哪个槽）。日志跨重启累积：`<安装根>\logs\dsh-ab.log`。
- 改 dsh 自身或做测试时把级别开到 **full** 方便排查（托盘第 3 项循环三档，只对本次运行有效）；**切槽、交回用户之前，把级别改回你开始时的那个**（要持久就改 `<安装根>\dsh-ab.toml` 的 `logs.level`，再重启 DSH-AB）。

## 台账（<安装根>\docs\）

- `PLUGINS.md`：每个插件一行——插件名、上游链接、本槽版本、用途、改动内容、改动原因、上游是否已修与最近核对日期；升级插件前逐条核对上游是否已修。
- `TODO.md`：每轮开工前清空，只写本轮；完成一项立刻打勾。

## 升级 DSH-AB 本身

用户要求升级 DSH-AB 时，就地对这次安装做（**别另建安装目录**），顺序是：

1. 取对应的更新包：仓库 `https://github.com/yemiao2745/DSH-AB` 的 Releases 里、`DSH-AB-<DSH-AB 版本>-update.zip`
   （一个 DSH-AB 版本一个 Release）。包里就是安装根的程序文件，**不含任何槽**。
2. **先提交一次快照**（安装根的 git），信息写清「更新到 <新版本> 之前」——回退就是取回这次提交。
3. 展开更新包，然后按新版覆盖安装根的程序文件：**先把安装根里除 `slot-a`、`slot-b`、`.git`、`state` 以外的目录整份删掉**（`docs`、`runtime`、`logs` 及任何别的目录），再覆盖上去。`state`、`dsh-ab.toml` 与两个槽必须原样保留；`DSH_AB.exe` 可能正在运行，**先把现有的改名、再把新的放到原位**，不许结束任何进程。
4. 包里那两份台账（`docs\PLUGINS.md`、`docs\TODO.md`）带着安装根占位符，把它替换成真实的安装根路径，**UTF-8 无 BOM**。
5. dsh 与托盘都不用重启，新版托盘下次启动生效。回退：`git reset --hard <那次快照>`（快照只跟踪程序文件与 `docs`，`runtime` 与两个槽不在里面）。
